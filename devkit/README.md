# devkit — installer and module library

The installer and module library that copies guardrails into target repos. In this document "factory" means your clone of this repo and "downstream" or "target" means a repo you install into. Distributes capability by **copy-on-build + version
stamp**: a target works fully with this repo deleted (never symlink, never runtime-
reference).

## Layout

```
<repo root>/
├── devkit/
│   ├── modules/<name>/
│   │   ├── MODULE.md     frontmatter (name, version, domain, depends-on, payload)
│   │   └── payload/      files copied into a target
│   ├── codex-modules/<name>/  Codex module catalogue (same metadata contract)
│   ├── install/
│   │   ├── devkit-install.sh  Claude entry point
│   │   ├── codex-install.sh   Codex entry point
│   │   └── _devkit.py          its implementation
│   └── tests/
│       ├── test-devkit-feedback.sh        the shipped test suite (see Tests)
│       ├── test-personal-path-guard.sh    path-guard test (see Tests)
│       ├── test-txn.sh                    transaction-library test runner (see Tests)
│       ├── test_txn.py                    transaction-library unit tests
│       ├── test-contract-v2.sh            module-contract test runner (see Tests)
│       ├── test_contract_v2.py            module-contract unit tests
│       ├── test-migration-v2.sh           2.0 migration test runner (see Tests)
│       └── test_migration_v2.py           regrouping, alias and migration tests
└── install/lib/
    └── txn.py            the transaction library _devkit.py imports 
```

The step-by-step guide to writing your own `modules/<name>/` is in the root `README.md`.

## Modules — one per domain

A module is one domain of the registry taxonomy (`domain:` in its `MODULE.md`), and every payload
file carries the mechanism it works by (`mechanism:`: BLOCK, ASK, DETECT, INSTRUCT, ROUTE or
VERIFY). The module body has three fixed sections (`## Prevents`, `## Procedure`, `## State`);
the installer copies them, with the domain and the per-file mechanisms, into the install manifest.

the test suite fails when it is edited by hand.

Codex modules live in `devkit/codex-modules/`: `codex-instructions` installs
`AGENTS.md` and detailed rules; `codex-command-rules` installs `.codex/rules/ostler.rules`;
`codex-hooks-core` installs `.codex/hooks.json` and branch, stash, and personal-path
notices; `codex-skill-template` installs a starter `SKILL.md`; and `codex-audit`
installs `.codex/devkit-audit.py`. The starter skill stays outside Codex's skill
discovery path until copied into `.agents/skills/` and customized.

## Use

```bash
# Install all modules into a target repo:
devkit/install/devkit-install.sh install /path/to/target-repo

# Install specific modules (deps auto-ordered):
devkit/install/devkit-install.sh install /path/to/target git-multi-session work-craft

# Bring an installed target up to this kit (also migrates a 1.x manifest, see Upgrading from 1.x):
devkit/install/devkit-install.sh update /path/to/target

# Check drift (runs the FACTORY's own copy of devkit-audit.py against the target —
# not the copy installed at <target>/.claude/devkit-audit.py; see Self-containment):
devkit/install/devkit-install.sh --check /path/to/target

# Record a deliberate downstream edit you may later fold back into your factory clone or contribute upstream (patch ledger, see below):
devkit/install/devkit-install.sh patch /path/to/target <managed-path> --reason "<why>"

# Codex: use the same commands and argument order:
devkit/install/codex-install.sh install /path/to/target-repo
devkit/install/codex-install.sh check /path/to/target-repo
devkit/install/codex-install.sh outdated /path/to/target-repo
devkit/install/codex-install.sh remove-module /path/to/target-repo codex-hooks-core
devkit/install/codex-install.sh recover /path/to/target-repo
```

Install stamps `<target>/.devkit-manifest.json` with per-file SHA-256 and the factory's
`source_commit`. The installer **refuses to clobber** modified-downstream or pre-existing
unmanaged files without `--force`. A refused file keeps its prior manifest
record, so a `pending-upstream` file survives a
re-install as an exact managed-path match. A file carrying a `devkit:forked` marker is
left alone (the target has taken ownership).

The two catalogues share the target manifest, lock, and journal. Installing or
removing a Codex module preserves Claude module records, and vice versa. `outdated`
reports only modules from the selected catalogue; `check` audits the entire manifest.
Codex hooks run only after project config trust and `/hooks` review. Their commands
resolve scripts from the Git repository root; installing `codex-hooks-core` requires
the target to be that root. If Git or a hook script later becomes unavailable, the
hook command exits without blocking Codex.
Codex command rules govern commands outside the sandbox and are not a substitute for
Claude Code's permissions. They match exact command prefixes, so alternate flags,
paths, and shell wrappers may need separate review. The Codex personal-path hook inspects file edit inputs
through `apply_patch` (including the `Edit` and `Write` matcher aliases); it does not
cover shell redirection or arbitrary programs.
The manifest-wide `source_commit` and `source_dirty` fields describe the latest
installer run; per-module fingerprints track each installed module's version.

## Tests

`devkit/tests/test-devkit-feedback.sh` is the shipped test suite (35 checks of the audit's
ledger handling and the `patch` command). Run it from a clone with a clean git checkout:

```bash
bash devkit/tests/test-devkit-feedback.sh
# expected last line:  35/35 passed
```

`devkit/tests/test-txn.sh` runs `devkit/tests/test_txn.py`, the unit tests of the
transaction library (`install/lib/txn.py`): crash recovery at every fault point, compare-and-swap,
locking and the fingerprint. It needs only
`bash` and `python3`:

```bash
bash devkit/tests/test-txn.sh
# expected last line:  <N>/<N> passed, 0 skipped
```

`devkit/tests/test-personal-path-guard.sh` checks that the path guard exempts only the user-level
config directory in your home folder and flags a repo-level `.claude` directory:

```bash
bash devkit/tests/test-personal-path-guard.sh
# expected last line:  6/6 passed
```

The Codex suite covers installation, mixed manifests, refusal, audit, hooks, and
command rule syntax. It needs PyYAML and a `codex` executable for the rule check:

```bash
python3 -m unittest devkit.tests.test_codex_installer -v
```

`devkit/tests/test-contract-v2.sh` runs `devkit/tests/test_contract_v2.py`: the `MODULE.md` contract
(domain, per-file mechanism, the three body sections), settings fragments from several modules,
the manifest projection, the `board` card renderer and the generated module table above. It needs
`bash`, `python3` and PyYAML:

```bash
bash devkit/tests/test-contract-v2.sh
# expected last line:  <P>/<T> passed, <S> skipped  (tests that need an optional prerequisite, such as the 1.x kit in git history or an optional input file, are skipped)
```

`devkit/tests/test-migration-v2.sh` runs `devkit/tests/test_migration_v2.py`: the 2.0 install compared with the
1.x kit (it materializes the 1.x tree from git history, so it skips in a copy without history), every verb with
a 1.x name, and the migration of a 1.x-installed target including injected failures. It needs `bash`,
`python3`, `git` and PyYAML:

```bash
bash devkit/tests/test-migration-v2.sh
# expected last line:  <P>/<T> passed, <S> skipped  (tests that need an optional prerequisite, such as the 1.x kit in git history or an optional input file, are skipped)
```

**Reading the last line.** A runner prints `<P>/<T> passed` or `<P>/<T> passed, <S> skipped`: `<P>` tests
passed out of `<T>` run, `<S>` of them skipped. A skip is a test that needs an optional prerequisite that is absent
(for example the 1.x kit in git history, or an optional input file). Skips are expected and are not failures. In this clone
`test-contract-v2.sh`, `test-decision-gating.sh`, `test-harness-governance.sh`, `test-migration-v2.sh` and
`test-work-craft.sh` therefore report some skips; `test-devkit-feedback.sh`, `test-txn.sh` and
`test-personal-path-guard.sh` report none. In every case `<P>` plus `<S>` equals `<T>`, the exit code is 0, and no
`FAILED` line is printed. A failure is any other result.

The feedback suite builds throwaway targets in a temp directory and removes them on exit; it needs
`bash`, `python3` and `git`, and touches nothing outside that directory.

## Patch ledger — the minimal upstream feedback loop

`check` classifies each manifest-managed file into one of four states:
`clean` / `modified-downstream` (fails) / `pending-upstream` (a deliberate downstream
fix you intend to copy back into your devkit clone — exits 0, or exits 2 as `STALE` if the file was edited
again since) / `forked`. A downstream edit becomes `pending-upstream` by running
`patch` (above), which stamps a `patched_pending_upstream` entry — `{path, sha256,
reason, date}` — pinned to the exact patched content, not the path forever: any further
edit re-fails until the ledger entry is refreshed (the STALE failure message prints its
own pre-filled refresh command). For every `pending-upstream` file, `check` also prints
a copy-paste command that appends the fix to a JSONL log on the machine running the check
(the audit prints its path); it is never auto-run. The log is a local JSONL record of the fixes you recorded with `patch`: review it with any JSON tool, or attach it to an issue when contributing a fix back to the kit (the kit takes issues, not pull requests). It is one file, `feedback.jsonl`, in a `devkit-feedback` folder under the devkit home (`$DEVKIT_HOME`, default `$HOME/.devkit`), or in `$DEVKIT_FEEDBACK_DIR` when you set that to an absolute path. Each line is `{"ts", "reason", "path"}`. A `mode: merge` file (for example
`settings.json` from `system-safety`) cannot carry a pending-upstream entry, because a merged
file's content is not a copy of the payload, so its sha256 cannot be pinned to one patched version (see the docstring of `validate_ledger` in `devkit/modules/audit/payload/devkit-audit.py`).

### What `check` covers

A `mode: merge` file (`settings.json`) stays `clean` while it is valid JSON and every permission pattern the
modules recorded is still in it. Losing a recorded pattern (including moving a `deny` or `ask` pattern into
`allow`) is `modified-downstream`, and so is `permissions.defaultMode` set to `bypassPermissions` (the row carries
a reason line). Hooks that return their own permission decision (for example an auto-allow `PreToolUse` hook) are
not inspected, nor is what any hook script does. `settings.local.json`, the personal settings file that Claude Code
layers over `settings.json`, is not read at all: a `bypassPermissions` mode, an `allow` entry or a hook set there goes
unreported.

## Upgrading from 1.x (kit 2.0)

Only relevant if you installed a 1.x release of this kit; new installs can skip this section.

Kit 2.0 regroups the 1.x modules by domain. `settings-baseline` is split into permission fragments inside
`system-safety` and `secrets-privacy`; `hooks-core` and `rules-core` are split across `git-multi-session`,
`secrets-privacy`, `work-craft` and `observe`. `audit`, `claude-md-kernel` and `skill-template` keep their names.
Most payload files have the same bytes; only the module that owns them changed. Four files that a 1.x
install also had changed in 2.0, and `update` overwrites them: `CLAUDE.md` (two bullets became optional
placeholders), `git-hygiene.md` (in `.claude/rules`), `SKILL.md` (the example skill, in
`.claude/skills/EXAMPLE-SKILL`) and `devkit-audit.py` (in `.claude`; it gained the `board` command). `update`
also adds two rules a 1.x target never had, `output-quality-standards.md` and `communication-style.md` (both in
`.claude/rules`), from `work-craft`. The split is not one-to-one either: `secrets-privacy` succeeds all three
retired names, so migrating a target that only had `rules-core` (by `update`, or by installing the `rules-core`
name) also installs the `secrets-privacy` settings fragment (five deny patterns for `.env` and secrets paths) and
three hook scripts (`stash-leak-check.sh`, `branch-similarity-check.sh`, `personal-path-guard.py`), none of which
that target had before. The hooks are only copied, never wired. `remove-module rules-core` removes those denies
again, along with the other modules the name maps to.

- **Old names still work for one minor version.** `install`, `update`, `outdated` and `remove-module` accept a
  1.x name, print one `DEPRECATED` line naming the 2.0 modules (and `2.1.0`, the release that removes the alias),
  and act on those modules. A name that is a real module is never treated as an alias.
- **Migrate with `update`.** `devkit-install.sh update <target>` rewrites the target's 1.x module records to the
  2.0 records in the same transaction as the file writes. If anything fails, run `recover`: the 1.x manifest comes
  back byte for byte. A target that never runs `update` keeps working: `check` passes, and `outdated` tells you
  to run `update`.
- **If you edited one of those four files, `update` refuses (exit 3, nothing written).** A filled-in `CLAUDE.md`
  is the usual case. The output is:

  ```
    REFUSE modified-downstream CLAUDE.md (use --force)
  [devkit] 1 file(s) refused (modified/unmanaged). Nothing was written. Re-run with --force to overwrite.
  ```

  To keep your file, put a line containing `devkit:forked` in it (for example `<!-- devkit:forked -->`) and run
  `update` again: the file is skipped (`skip   forked          CLAUDE.md`) and `check` reports it as `OK forked`.
  To take the kit's version, copy your file somewhere safe first, then run `update <target> --force`; `--force`
  overwrites every modified file, not only that one.
- **Partial migration is safe.** `install <target> rules-core` migrates only what that name maps to (including the
  footprint above); the other 1.x records stay valid until you run `update`. A 1.x record that is still installed
  keeps providing its permission patterns, so removing a 2.0 module never strips a pattern the 1.x record still
  provides.
- **Patterns from before ownership tracking are never removed.** A 1.x record does not say which permission
  patterns you added yourself, so after migration `remove-module` deletes only the patterns the 2.0 install
  itself added. Any fragment pattern that was already in `settings.json` is recorded as `legacy_unclaimed` and
  stays. Both `update` and `remove-module` print one line, for example
  `  kept   5 pattern(s) in .claude/settings.json that predate ownership tracking (they may be yours; delete by hand if unwanted): ...`.
  If you do not want a kept pattern, delete it from `settings.json` by hand.
- **`update` with nothing installed** installs nothing and says so; it never falls back to the whole kit.
- Each manifest records the kit version (`kit_version`).

## Settings fragments and the board

Several modules may each `mode: merge` a fragment into the same `settings.json`; they merge in install
order, the manifest records the permission patterns each module contributed (`merged` in its record),
and `remove-module` un-merges exactly those patterns. A pattern two modules both contributed stays until
both are removed; your own `allow` entries and any pattern that was in the file before the install are
never touched.

With the factory deleted, `python3 .claude/devkit-audit.py board` prints one card per installed module
(purpose, surfaces, principles, procedure, state), read from the manifest and from the hooks block of
the `settings.json` in the target's `.claude` folder.

## Self-containment

Module payloads are generic templates.
The **installer** (`devkit-install.sh` / `_devkit.py`) needs PyYAML (`python3 -m pip install pyyaml`) to read
`MODULE.md`; without it it exits 1 with `ModuleNotFoundError: No module named 'yaml'`. Only the `audit` payload
is stdlib-only Python, so a target can self-check with this factory
deleted.

## Transactions and locking

`devkit-install.sh` runs on a crash-safe transaction library
(`install/lib/txn.py`). Every mutating
command plans everything read-only first, then (only if there is something to commit)
takes an exclusive lock, settles any interrupted transaction, re-plans, and applies one
journaled transaction whose manifest rename is the commit point. A refusal therefore
writes nothing at all: no files, no manifest change, no new target directory, and no lock
file. Each planned write or delete records the file state the plan saw, so if someone edits
a file between planning and applying, the install stops with exit 3 and leaves their edit
alone. `check` and `outdated` take the lock in shared mode (they wait for nothing, they
just refuse with exit 4 while an install is running), so they never report a half-applied
tree. A reader on a target that has no lock file yet does not create one; if an install
starts while the reader is running, the reader exits 4 when it finishes and prints nothing
from that read (retry it). The refusal rounds of `install`, `remove-module` and `patch` and
the `recover` "nothing to do" check behave the same way. devkit assumes it manages every path a module payload names; do not point other tools at those paths.

| Command | What it does |
|---|---|
| `update <target> [module ...]` | `install` over the modules the manifest records (1.x names mapped to 2.0), rewriting 1.x records to 2.0 in one transaction |
| `outdated <target> [module ...]` | one line per installed module whose factory payload changed: `devkit: <module> outdated (installed <fp>, source <fp>) -> devkit-install.sh install <target> <module>`. No output = current. Read only, exits 0 |
| `remove-module <target> <name> [--force]` | removes a module's clean files and its manifest record. Modified files are refused (exit 3) unless `--force`. Deselecting a module on `install` never prunes; use this |
| `install ... --allow-dirty` | install from a factory checkout with uncommitted changes under the selected modules (or a non-git factory). Without it: exit 7. The manifest records `source_dirty=true` |
| `readme [--check]` | regenerate the module table above from every `MODULE.md` (`--check` exits 1 when the committed table differs) |
| `recover <target>` | finish or roll back a crashed install; prints `no interrupted transaction` when there is nothing to do |

Exit codes: `0` ok · `1` usage/internal · `3` refusals, nothing written (modified-downstream
or unmanaged files; re-run with `--force`) · `4` locked by another run · `6` interrupted
transaction pending (`check` / `outdated`; run `recover`) · `7` dirty factory checkout
(commit, or `--allow-dirty`) · `8` validation / confinement error (path escapes the target,
symlinked directory, two destinations that are the same file modulo case or Unicode
normalization, or a target that is the factory checkout itself, inside it, or contains it).
